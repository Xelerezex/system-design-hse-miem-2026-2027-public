# Спецификация `soldout-v2`: динамическое ценообразование

Версия: `lesson-5` / 2026-11-13. Владелец: исполнитель HW1. Статус: проект для трека А, согласована вариация V2.

## 1. Легенда и контекст

На стадионе цена билета определяется сектором и количеством **оплаченных** мест этого сектора на момент создания hold. За каждые N=100 проданных мест цена повышается на X=10%. Покупатель видит зафиксированную сумму при hold и платит именно ее, даже если за время оформления другие покупатели пересекли новую ценовую ступень.

Главный риск — конкуренция на пороге 100, 200, … продаж: два запроса не должны получать цену из несогласованных состояний базы. Ошибка приводит к неверной сумме заказа, потере доверия и необходимости компенсаций. Условия продажи мест, идемпотентность и архитектурные границы из `spec/soldout.md` сохраняются.

## 2. Роли

| Роль | Что делает |
|---|---|
| Покупатель | Получает admission-токен, создает hold, проверяет цену, оформляет и оплачивает заказ. |
| Администратор | Задает базовую цену и параметры ступеней для сектора до открытия продаж. |
| Эмулятор PSP | Обрабатывает оплату согласованной суммы заказа. |
| Оператор | Сравнивает задержки и проверяет инварианты после нагрузки. |

## 3. Функциональные требования

| ID | Требование | В HW1 |
|---|---|---|
| FR-V2-1 | Для `(event_id, sector_id)` хранить базовую цену в минорных единицах, N и X; не читать цену из `TICKET_PRICE_MINOR` на пути V2. | Да |
| FR-V2-2 | Вычислять ступень `k = floor(sold_count/N)`, где `sold_count` — число подтвержденных после успешной оплаты мест данного сектора и мероприятия. | Да |
| FR-V2-3 | Цена `P(k) = round_half_up(P0 * (1 + X/100)^k)` в минорных единицах; при P0=500000, N=100, X=10: k=0 → 500000, k=1 → 550000, k=2 → 605000. | Да |
| FR-V2-4 | Атомарно зафиксировать `price_minor` в hold при создании; значение не меняется после создания, в том числе после истечения hold, отмены заказа и перехода ступени. | Да |
| FR-V2-5 | `orders.amount_minor` вычислять как сумму `holds.price_minor` всех позиций заказа, не делать повторного запроса актуальной цены. | Да |
| FR-V2-6 | При `pay` использовать сохраненный `orders.amount_minor`; повторный pay и повторное создание заказа с тем же ключом идемпотентны. | Да |
| FR-V2-7 | При параллельных hold/pay чтение количества продаж и фиксация цены должны иметь определенный порядок относительно подтверждения оплаты; недостаточно неконсистентной проекции карты зала. | Да |
| FR-V2-8 | Успешная оплата увеличивает `sold_count` ровно на число впервые подтвержденных мест. Неуспешная и повторная оплата не увеличивают счетчик. | Да |
| FR-V2-9 | API ответ hold содержит `price_minor`; API заказа содержит `amount_minor`, соответствующий сумме hold. | Да |
| FR-V2-10 | Стандартные I1–I6 продолжают выполняться; события, от которых зависит обязательство перед покупателем, пишутся через outbox. | Да |

## 5. Расчет нагрузки

1. **Допущения.** В окно 60 секунд допущено 1800 покупателей; каждый выполняет один полный checkout. Лабораторный admission не ограничивает этот поток. 40% запросов целенаправленно выбирают один сектор для пересечения нескольких ценовых порогов; остальные 60% равномерно распределены по трем другим секторам (по 20%).
2. **Интенсивность продаж.** `1800 / 60 = 30` успешных покупок/с при наличии свободных мест. Это 1800 подтверждений и 1800 созданных заказов за прогон.
3. **API-частота.** Один путь: seatmap summary (1), sector seatmap (1), join (1), hold (1 + повторы при 409), order (1), pay (1), tickets (1). При коэффициенте попыток hold 1.2: `(6 + 1.2) × 30 = 216 HTTP RPS`; из них около 36 RPS — hold, 30 RPS — pay.
4. **Параллелизм.** По закону Литтла, при среднем времени полного цикла 0.8 с: `L = λW = 30 × 0.8 = 24` активные сессии. Устанавливаем 100 VU для сохранения целевой скорости при задержках до 3.3 с.
5. **Трафик.** При ответе карты сектора ~32 KiB и 30 чтениях/с: `30 × 32 KiB = 960 KiB/с ≈ 7.86 Мбит/с` без протокольных накладных расходов; за 60 с ~56.25 MiB.
6. **Емкость.** 4 сектора × 1000 мест = 4000 мест на мероприятие. Прогон в 1800 оплат укладывается в емкость одного незатронутого мероприятия. На горячем секторе ожидается `1800 × 0.40 = 720` оплат, то есть переходы через 100/200/300/400/500/600/700.
7. **Рычаг нагрузки.** `PRICE_STEP_SEATS=N` задает частоту смены цен. `PRICE_STEP_PERCENT=X` управляет ценовой амплитудой; k6 `rate` и доля горячего сектора управляют давлением на конкурентный участок.

В честном сравнении оптимизаций нужны одинаковые данные перед стартом (количество уже оплаченных мест по секторам), одинаковый случайный seed сценария, одинаковые лимиты и та же версия k6. Стенд с уже проданными местами не является эквивалентным чистому baseline.

## 6. Ограничения

- Исходник — только `lesson-5`; трек А, без использования реализации ветки `hw1/v2-base`.
- Go 1.27, PostgreSQL 17, Valkey, Docker Compose, существующие модули и `.go-arch-lint.yml`.
- Миграции создаются новыми парами `*.up.sql` / `*.down.sql`; старые миграции не изменяются.
- SQL модулей не обращается напрямую к чужим таблицам; цена сектора получается через `catalog/api`, а принадлежность места сектору проверяется через каталог.
- Нет использования асинхронной проекции `catalog_seat_state` в качестве источника цены: проекция может отставать.
- Платежи и их подтверждение наследуют ограничения ADR-003 и исходной системы; дефекты исходного `hold` не входят в две оптимизации HW1.

## 7. Модули и владение данными

| Модуль | Ответственность | Владеет данными |
|---|---|---|
| `catalog` | Правила цены для `(event, sector)`, идентификация сектора места | `sector_prices` (новая таблица), `sectors`, `seats` |
| `booking` | Атомарная фиксация цены hold, сумма заказа, учет подтвержденных продаж | `holds.price_minor`, `holds.sector_id`, `orders`, `order_items`; при оптимизации — `sector_sales` |
| `payment` | PSP и идемпотентность платежа по сумме заказа | `payments` |
| `ticketing` | Билеты на оплаченные места | `tickets` |
| `platform/outbox` | Надежные события по правилам конституции | `outbox` |

Схема данных: `sector_prices(event_id, sector_id, base_price_minor, step_seats, step_percent)`, `holds(..., sector_id, price_minor, ...)`. Для первоначального варианта `sold_count` определяется по подтвержденным hold внутри booking, без JOIN к `catalog` в SQL. Миграция 0022 создает правила как для существующих событий, так и для будущих событий через триггер при INSERT в `events`. Исторические цены восстановлены из сумм существующих заказов. Дополнительно `holds.sold_count_at_hold` фиксирует значение, по которому определена ступень. Хранилище агрегатов `sector_sales` допускается **только после измерения и решения об оптимизации**.

Граница: `booking → catalog.api`; внутренняя структура `catalog` недоступна `booking`. Связь `booking` с `payment` — существующий порт из `booking/api`.

## 8. Инварианты

- **I1–I6.** Сохранены из `docs/constitution.md` и существующего чекера.
- **I7.** Для каждого заказа `orders.amount_minor = SUM(holds.price_minor)` по `order_items` этого заказа. Проверка новым SQL-запросом в `tools/invariant-checker`; 0 нарушений после нагрузки.
- **I8 (тестовый).** Цена созданного hold соответствует допустимой ступени в момент сериализованного чтения подтвержденных продаж и впоследствии неизменна. Проверка конкурентными integration-тестами и раздельной фиксацией факта создания; ретроспективная проверка только по текущему `sold_count` некорректна.
- **I9 (при агрегатах).** `sector_sales.sold_count` совпадает с числом подтвержденных мест по `(event_id,sector_id)`; 0 расхождений после нагрузки. Добавить в checker вместе с агрегатом.

## 9. API и события

Существующий путь: `POST /v1/events/{id}/queue/join` → `POST /v1/holds` → `POST /v1/orders` → `POST /v1/orders/{id}/pay` → `GET /v1/users/{id}/tickets`.

`POST /v1/holds` и `GET /v1/holds/{id}` должны возвращать `price_minor` (integer int64, минорные единицы). `POST /v1/orders` и `GET /v1/orders/{id}` возвращают уже существующий `amount_minor`, вычисленный из hold. Изменения отражаются в `api/openapi.yaml`.

Для новой функциональности не требуется публиковать отдельное событие: используем существующий `OrderPaidEvent` с outbox. Если при реализации окажется необходимым новое надежное событие, его следует записывать в ту же транзакцию через `platform/outbox` и описать в `docs/asyncapi.yaml`.

## 10. Не в scope

Вторичная перепродажа, возвраты, мультвалютность, динамическое снижение цены, админ-редактирование правил после открытия продаж, масштабирование вне lite/full стенда, исправление исходных ограничений I3/I4/I6 (они документируются отдельно).

## 11. Открытые вопросы

1. Подтвердить необходимость админ-API изменения цены: в HW1 достаточно данных, задаваемых миграцией/seed; отдельный admin endpoint не включен в текущий план.
2. Уточнить правила округления: предлагаем `round_half_up` после вычисления ступени без float (decimal/rational арифметика). Это решение должно быть одинаковым в Go и тестах.
3. Проверить по коду, где окончательно подтверждаются hold и оплачивается заказ, до выбора единой точки синхронизации счетчика продаж.
